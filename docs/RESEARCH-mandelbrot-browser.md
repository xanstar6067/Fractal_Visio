## 2. Ключевая идея: кадр — это не буфер

Результат счёта у них — не «текущая картинка», а `compute/Result`:

```java
public class Result {
    public Bitmap bitmap;
    public Location location;    // вид, для которого этот битмап посчитан
    public int resultQuality;    // во сколько раз он грубее 1:1
    public int phase;
    ...
}
```

Битмап **никогда не переписывается под новый вид**. Вместо этого при отрисовке считается матрица:

```java
// PictureView.computeDrawMatrix, сокращённо
double d = mCurrentLocation.zoom / result.location.zoom;
// ... смещение центров, поворот через transformation ...
matrix.setPolyToPoly(mSrcPoints, 0, mDstPoints, 0, 4);
```

и `onDraw` рисует до трёх слоёв, у каждого своя матрица:

```java
canvas.drawBitmap(mResult.bitmap, mMatrix, null);              // текущий результат
canvas.drawBitmap(mPreviousResult.bitmap, mPreviousMatrix, p); // затухающий предыдущий
canvas.drawBitmap(mPartialResult.bitmap, mPartialMatrix, null);// частичный
```

**Три следствия, и все три были нашими проблемами.**

*Накопление ресэмплинга.* Наш `ReprojectFrame` варпил единственный буфер на месте, каждый кадр
жеста. Панорама в 60 кадров = 60 nearest-neighbour пересэмплирований уже пересэмплированного.
У них исходный битмап сэмплируется ровно один раз, в момент отрисовки, с фильтрацией.

*Стоимость.* Варп был полнокадровым `Parallel.For` по каждому пикселю, на тех же ядрах, которые
в этот момент считали фрактал. На 1080p с полями — около 2.6 Мпикс за кадр жеста, отобранных
у рендера. У них это одна матрица.

*Невозможность иметь больше одного кадра.* Раз буфер и есть вид, второй вариант хранить негде.

## 3. Оверскан у них динамический

`Request.scaleOverhead` — коэффициент, на который делится зум запроса, то есть во сколько раз
шире экрана считается кадр. Он не константа:

| Ситуация | Значение | Ширина поля | Где |
|---|---|---|---|
| Ручное перетаскивание, базовое | `0.7` | 1.43× | `ComputingThread:151` |
| Предсказанный бросок | `min(0.7, 1/(dist·⅔ + 1.2))` | до 1.43× | `FadeMoveController.predictDrag` |
| **Fade-зум на отдаление** | до `0.5` | **2.0×** | `FadeMoveController.predictZoomAndRotation` |
| Поворот | `MoveUtils.rotationSafeScaleFactor(shortEdge, longEdge, angle)` | точная геометрия | `finalizePredictRotation` |

Наш прежний `CpuOverscan = 0.04…0.06` давал поле 1.08–1.12× — этого хватает на зум-аут в 1.1 раза,
а пинч на отдаление легко даёт 2–4× за жест. Поле было спроектировано под панораму и применялось
к зум-ауту, где оно на порядок мало. Это и была главная причина оставшихся артефактов.

**Асимметрия, которую они используют.** Для зум-аута нужны не лишние пиксели, а грубее посчитанная
более широкая область: они не увеличивают битмап, они делят `location.zoom`
(`Location.changeZoomMoveMode(scaleOverhead)`). Тот же буфер покрывает вдвое большее поле вдвое
грубее. Во время зум-аута картинка и так сжимается, разрешение там не нужно.

## 4. Предиктивный рендер

`FadeMoveController implements MovementPredictor` — самая глубокая идея во всём приложении.
Последовательность на каждый запрос:

1. Из скользящих окон `dragList` / `zoomList` / `rotationList` выводятся `dragSpeed`, `zoomSpeed`,
   `rotationSpeed`; есть модель торможения `SmoothMovementDeceleration` с методами
   `distance`, `time`, `distanceExp`, `timeExp`.
2. Оценивается длительность рендера каждой фазы:
   `lastComputedResult.effectiveComputingTime * pow(4, lastResult.phase - candidate)`.
3. Перебором выбирается фаза, у которой максимальна «полезная жизнь» кадра: он ещё покрывает
   вьюпорт, когда прилетит, и какое-то время после.
4. **Рендерится та точка, где вид будет в момент прилёта кадра**, а не где он сейчас:
   `request.location.changeZoomMoveMode(distanceExp(...))`, `request.location.drag(...)`.
5. `scaleOverhead` подбирается так, чтобы покрыть остаточное движение на интервале
   `[resultEntryFade, resultExitFade]`.

Мы рендерим текущее положение. Пока долетает даже проход step-16, вид уехал — самый свежий кадр
уже устарел. Предсказание делает свежайший кадр самым подходящим.

Отложено: нужен оценщик времени рендера по предыдущему результату, которого у нас пока нет.
См. этап 11 в `ARCHITECTURE.md`.

## 5. Кэш кадров и `computeClip`

```java
// PictureView.computeClip — насколько вьюпорт вылезает за покрытие результата,
// нормировано размером экрана. <= 0 означает «покрыт полностью».
protected double computeClip(Location location) { ... }

protected boolean checkClipForQuickCorrection() {
    if (computeClip(mResult.location) > 0.25d) return true;
    return mMoveMode.isAutoZoomIn() && mCurrentLocation.zoom / mResult.location.zoom > 4.0d;
}
```

При авто-зуме держится до 5 кадров (`mFrameList`), отсортированных по зуму; каждый тик выбирается
кадр с наименьшим clip, пропущенные освобождаются, смена кадра кросс-фейдится за `FULL_BLEND_TIME`
(150 мс).

Прямой аналог `mFrameList` нам даёт мало: при зум-ауте предыдущие кадры покрывают **меньшую**
область и бесполезны. Полезен ровно один дополнительный слой — широкий и грубый. Мера `clip`
при этом нужна целиком: она решает, когда его перерисовывать.

## 6. Планировщик счёта

Четыре приёма, которые стоит держать в голове при работе над этапом 9 (Burst):

- **Тайм-слайсинг.** `mStepIterationsTarget` — сколько итераций ядро проходит за один запуск;
  подстраивается в рантайме под `TARGET_STEP_TIME = 50 мс` (`ComputingThread:632-649`) и кэшируется
  по паре `(fractal, precision)`. Целевое время всего запроса при ручном движении — 250 мс.
- **Persistent threads.** `forEach_Process` идёт не по пикселям, а по массиву «потоков»:
  `31 × 1072` int (`Computer:303`) — 1072 воркера с возобновляемым состоянием, каждый сам берёт
  следующий пиксель. Это динамическая балансировка: стоимость пикселя во фрактале различается
  в сотни раз.
- **Слияние запросов.** `Request.mergeWaitingRequest` / `mergeCalcRequest` — ожидающие запросы
  сливаются, а не копятся.
- **REPAINT без пересчёта.** Смена палитры/света/эффекта идёт отдельным типом запроса поверх
  сохранённых `inumber` / `fnumber`, без пересчёта орбит.

Плюс то, чего у нас нет вовсе: **smooth-раскраска** (дробная часть номера итерации хранится
рядом с целой, `mSmoothIterAllocations`) и **supersampling** 2×2…9×9 с RMS-усреднением и
adaptive-режимом через edge detection.

## 7. Математика глубины

### 7.1 Что там на самом деле

Никакой пертурбации, никакого series approximation, никакого BLA. Прямой перебор в произвольной
точности:

```java
// Location.computePrecision(pictureSize, currentPrecision)
bits = ceil(-log2((4.0 / pictureSize) / zoom)) + 2;
if (bits <= 53)  precision = 0;                       // forEach_Process    (fp64)
else             precision = ceil(bits / 32);         // forEach_Process_LD (лимбы)
```

`compute/LongDouble` — знак + целая экспонента + `long[]` 32-битных лимбов, максимум 32 лимба
(`mLdPosition = new int[68]` = `(32 + 2) * 2`), то есть 1024-битная мантисса. Отсюда номинальный
`Fractal.MAX_ZOOM = 1e300`. Арифметика — умножение столбиком, O(лимбов²).

Компенсируют не алгоритмом, а планированием: `stepIterationsTarget` = 10000 для fp64 и 1000 для LD,
лимит итераций 100000, фазы coarse-to-fine, гистерезис в `computePrecision` (точность не понижается,
пока требование не упадёт заметно ниже границы). Их собственный tutorial признаёт: глубокий зум
начинается около 5e12, после 1e100 «очень долго».

**Вывод: это грубая сила с отличным расписанием.** Изощрённость в конвейере, не в числах.

### 7.2 Переносимо ли

`LongDouble` портируется и он Burst-совместим — чистая целочисленная лимбовая арифметика,
ни `decimal`, ни `BigInteger` в горячем цикле, `NativeArray<uint>` + `IJobParallelFor` заработает.

Но это покупает диапазон, а не скорость: на 4 лимбах (128 бит) мы медленнее fp64 в 10–20 раз
на итерацию, на 32 — в сотни. Получится 1e-300 на скорости «оставь на ночь».

**Рекомендация: не портировать `LongDouble`.** Правильный обмен — пертурбация: одна опорная орбита
в высокой точности (managed, одна точка, дёшево), затем каждый пиксель итерирует дельту в fp64.
Стоимость на пиксель остаётся fp64-шной независимо от глубины; глубина ограничена только точностью
опорной орбиты. Нужны детекция глитчей (критерий Pauldelbrot: `|δz|` дорастает до порядка `|Z|`)
и перебазирование; BLA дополнительно пропускает тысячи ранних итераций. Это то, почему современные
глубокие зумеры интерактивны на 1e-1000.

### 7.3 Наш реальный потолок сейчас — не арифметика

| Что | У нас | У них |
|---|---|---|
| Лимит итераций | `RenderQuality.MaximumIterations = 2048` | 100000 |
| Минимальный масштаб | `MinimumScale = 1e-24` | ~1e-300 |
| Предел типа координат | `HighPrecision` = `decimal`, ~1e-28 | `LongDouble`, 1024 бита |
| Предел семплера | `DoubleDouble`, ~32 знака → ~1e-30 | — |

При масштабе 1e-24 нужно на порядок больше 2048 итераций, чтобы картинка вообще что-то значила:
изображение станет сплошным «интерьером» задолго до того, как кончится точность. **Первое узкое
место глубины — бюджет итераций и способность его себе позволить, а не арифметика.**

Что из их математического слоя стоит взять до всякой пертурбации:

- формула нужной точности через **размер картинки**, а не только зум (`bits ≈ log2(pictureSize · zoom / 4) + 2`);
  при офскрин-съёмке в 4K требуется на пару бит больше, чем на телефоне;
- **гистерезис** при переключении тира точности;
- **адаптивный бюджет итераций от предыдущего кадра**, а не от формулы:
  `limit = minIterations(наблюдённый в этом виде) + detailLevel` (`ComputingThread.estimateIterationLimit`).

## 9. Инварианты, появившиеся после переноса

- **Рендерер не варпит свои пиксели.** Опубликованный кадр — картинка одного `ViewState`; следовать
  за жестом — задача композитора. Возврат репроекции вернёт и накопление ресэмплинга, и трату
  ядер посреди жеста.
- **Публикация только на границе прохода.** Пока первый проход нового запроса не покрыл буфер
  целиком, текстура держит предыдущий кадр вместе с его `PublishedView`. Это корректная картинка
  другого вида, а не наполовину корректная картинка этого.
- **Оверскан меняет поле, а не размер буфера.** Буфер выделяется один раз на разрешение экрана;
  `fieldFactor` меняет то, какую часть буфера видит зритель. Расширение поля стоит разрешения
  во время жеста, а не времени.
- **Широкий слой существует ради зум-аута и только ради него.** Он намеренно плохой: несколько
  сотен пикселей, один-два воркера, перерисовка только когда зритель подходит к краю покрытия.
- **Тайлы выравнены по 16.** Пропуск «уже посчитано в грубом проходе» проверяет абсолютные
  координаты пикселя; тайл, начавшийся не по сетке, даст шов.
